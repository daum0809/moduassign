# 실험 02: 권한 모드만 바꾸면 기록 없는 조건도 빨라지는가

- 실험 01의 돌아보기에서 나온 해석을 검증하는 후속 실험이다. 해석은 "B가 느린 것은 셸 쓰기가 권한에 거부된 뒤 재시도했기 때문"이다.
- 도구·모델·작업·요청 문장은 실험 01과 같다(Claude Code 2.1.299 headless, `claude-sonnet-5-5`, fixture/, B와 같은 요청 문장, notes 없음).
- 사전 등록: [PREREGISTRATION-02.md](PREREGISTRATION-02.md) (실행 전 커밋 `3f8fda8`)
- 실행일: 2026-10-16, 30세션 (리허설 1회는 제외)

## 1. 왜 권한 "모드"를 바꿨나

실험 01 B 조건의 거부 4건을 다시 읽어 보니, allow 규칙이 없어서 거부된 것이 아니었다.
**Claude Code의 셸 보안 검사**에서 나온 거부였다.

| 거부 메시지 | 나온 곳 |
|---|---|
| `Contains brace with quote character (expansion obfuscation)` | parse-log heredoc 3건 (f-string의 `{r['time']}`) |
| `Parser skipped input between top-level statements` | fix-failing heredoc 1건 |

이런 검사는 allow 규칙(`Bash(cat:*)` 등)을 넓혀도 풀린다는 보장이 없다. 그래서 조작 항목을 **권한 모드**로 골랐다.
`bypassPermissions`는 교안 권고(격리 환경에서만)에 따라 쓰지 않았다.

| 작업 | 판정 조건 | 결과 |

**판정: 부분 지지.**

- auto 모드는 권한 거부를 10건에서 0건으로 **확실히 없앴다.**
- parse-log에서는 그만큼 빨라졌다.
- fix-failing은 거부가 사라져도 거의 빨라지지 않았다. "권한 거부가 느린 원인"이라는 실험 01의 해석은 **parse-log에만 맞고 fix-failing에는 충분하지 않다.**

참고로 P0에서 거부가 다시 나왔으므로(10건) 비교의 전제는 성립했다. 실험 01의 B(4건)보다 많은데, 실험 01에는 없던 PowerShell 구문 오류 거부 4건이 섞였기 때문이다.

## 4. 사후 분석: 실제로 시간을 정한 것은 무엇인가

> 이 절은 **사전 등록에 없던 탐색적 분석**이다. 판정에는 쓰지 않는다. 다음 실험의 가설로만 쓴다.

fix-failing이 왜 안 빨라졌는지 보려고, 실험 01·02의 2차 시도 57회 전부에서 시간을 둘로 나눴다.
하나는 `result.duration_api_ms`(모델 API 시간)이고, 다른 하나는 나머지(도구 실행, CLI 시작 등)다.

| 작업·조건 | 벽시계 중앙값 | API 시간 | API 밖 시간 |
|---|---|---|---|
| fix-failing A (exp01, notes) | 53.1 | 10.8 | 42.3 |
| fix-failing C (exp01, 위약) | 54.2 | 13.9 | 39.4 |
| fix-failing B (exp01) | 74.4 | 10.6 | 63.1 |
| fix-failing P0 (exp02) | 77.4 | 10.4 | 65.5 |
| fix-failing P1 (exp02, auto) | 72.5 | 12.6 | 63.0 |

**조건 사이의 차이는 거의 전부 API 밖 시간에서 났다.** 모델이 생각하는 시간은 비슷했다.

그래서 API 밖 시간을 도구 호출 종류로 회귀했다(57회).

> API 밖 시간 ≈ 37.8초 + **7.0초 × 셸(Bash/PowerShell) 호출 수** − 0.8초 × 기타 도구(Read/Glob/Write) 호출 수

| 셸 호출 수 | 시도 수 | API 밖 시간 중앙값(s) |
|---|---|---|
| 1 | 30 | 41.0 |
| 2 | 12 | 50.6 |
| 3 | 11 | 56.4 |
| 4 | 4 | 65.2 |

**이 Windows 환경에서는 셸 호출 1회에 약 7초가 들고, Read·Glob·Write는 거의 공짜였다.**
이렇게 보면 두 실험의 결과가 한 줄로 설명된다.

- **실험 01의 A·C**: "notes를 먼저 읽어라"는 문장 때문에 Glob·Read로 시작했다. 셸은 대부분 테스트 실행 1회만 썼다(6회 중 5회). 그래서 빨랐다.
- **실험 01의 B, 실험 02의 P0·P1**: 셸로 테스트부터 돌리고, 셸로 파일을 보고, 셸 heredoc으로 썼다. 셸 호출이 2~4회였다.
- **auto 모드**: 거부를 없애서 "거부 → Write로 재시도"의 한 단계는 줄였다. 하지만 셸 위주로 일하는 경로 자체는 바꾸지 않았다.
  parse-log는 거부가 5/5회라 줄일 단계가 많았다. fix-failing은 거부가 2/5회뿐이라 효과가 작았다.

## 5. 돌아보기

- 실험 01의 1단계 불편(세션이 바뀌면 지난 경험이 사라져 시간이 아깝다)을 따라가 보니, **이 환경에서 측정되는 시간은 기억보다 "모델이 어떤 도구로 일하느냐"에 더 크게 좌우됐다.**
- 그 경로를 바꾸는 하네스 장치는 세 가지였다.
  - **요청 문장**: "먼저 읽어라". 효과가 가장 컸다.
  - **권한 모드**: 거부를 없앤다. 효과는 작업에 따라 달랐다.
  - **notes의 내용**: 효과가 확인되지 않았다.
- 셸 1회 7초는 이 PC(Windows, Git Bash)의 특성일 가능성이 크다. macOS나 Linux에서는 셸 비용이 작아서 같은 차이가 나지 않을 수 있다.
  이건 **도구의 기능이 아니라 실행 환경이 원인 후보**라는 뜻이다. 다음에 고정하거나 바꿔 봐야 할 조건이다.
- **약점**:
  - 사후 회귀는 무작위 배정이 아니다. 셸 호출 수를 정하는 무언가(작업의 난이도, 모델의 첫 판단)가 시간에도 영향을 줬을 수 있다.
  - `duration_api_ms`가 정확히 무엇을 포함하는지는 공식 문서로 확인하지 않았다(미확인).
