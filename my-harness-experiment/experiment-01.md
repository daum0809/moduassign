# 실험 01: notes/ 경험 기록은 같은 작업의 두 번째 시도를 빠르게 하는가

- 도구: Claude Code 2.1.299 (Windows, headless `claude -p`)
- 모델: `claude-sonnet-5-5`
- 실행일: 2026-10-16
- 사전 등록: [PREREGISTRATION.md](PREREGISTRATION.md) (실행 전 커밋 `1d3ebe2`, 측정 코드 보정 `bdf9d39`도 데이터 수집 전)

## 1. 불편과 가설

### 불편 (1단계)

LLM과 사업 구상을 여러 번에 걸쳐 이야기할 때 반복해서 멈춘 장면이 두 가지 있다.

1. **새 대화를 열면 앞서 함께 정리한 사업 구상을 전부 잊는다.**
   지난번에 정한 방향과 조건을 처음부터 다시 설명해야 했다.
   설명을 다시 하는 동안 실제 구상은 앞으로 나가지 않았다.
2. **한 창에서 길게 이야기하면 앞에서 정한 것들을 헷갈린다.**
   대화 앞부분에서 정한 조건을 뒤에서 섞거나 바꿔 말했다.
   그래서 다시 바로잡는 데 시간을 썼다.

결과적으로 **매번 다시 설명하고 바로잡는 데 시간이 아까웠다.**
Claude Code로 과제를 할 때도 같은 일을 겪었다.
지난 과제(local-rag-chatbot)에서는 "2B 모델이 숫자를 빠뜨려서 시스템 메시지를 바꿨다" 같은 결정을 다음 세션이 잊지 않게 하려고 CLAUDE.md에 직접 적어 넣어야 했다.

(사업 구상의 구체적인 내용은 공개 저장소라 적지 않는다.)

이 실험은 이 불편 가운데 1번, **세션이 바뀌면 지난 경험이 사라진다**를 다룬다.
대화로 하는 구상은 "잘 됐다"를 객관적으로 재기 어렵다. 그래서 같은 구조의 문제를 테스트로 성공을 판정할 수 있는 코딩 작업으로 옮겨 측정했다.
옮기는 과정에서 생긴 차이는 6장에서 한계로 다룬다.
2번(긴 대화 안에서의 혼동)은 컨텍스트 관리 쪽 문제라 이번 조작 항목에서 뺐다. 7장 다음 실험 후보로 남긴다.

### 원인 의심

이 불편이 정말 하네스의 메모리 기능 부재에서 오는지는 확실하지 않다. 다른 원인 후보:

- **모델**: 모델이 처음부터 테스트를 꼼꼼히 읽는다면 기록이 없어도 함정을 피한다.
- **작업 난이도**: 작업이 쉬우면 기록이 있든 없든 한 번에 끝난다.
- **요청 문장**: "테스트를 먼저 읽어라" 같은 문장 하나가 기록보다 효과가 클 수 있다.
- **실행마다의 편차**: 같은 조건에서도 시간이 크게 흔들린다.

### 가설 (2단계, 반증 가능)

> 같은 작업을 다시 풀 때, 첫 시도에서 얻은 접근법·오류·해결을 `notes/`에 남기고 두 번째 시도에서 그 기록을 먼저 읽게 하면,
> 기록 없이 시작할 때보다 두 번째 시도의 소요 시간이 10% 이상 짧고, 테스트 통과까지 시도 수는 같거나 적다.
> 그리고 이 효과는 "notes를 먼저 읽으라는 지시"가 아니라 기록의 **내용**에서 온다.

반대 결과가 나오면 가설은 틀린 것이다. 기록이 있어도 시간이 줄지 않거나, 위약 기록과 차이가 없으면 기각한다.

### 도구 선택 이유

평소 쓰는 도구가 Claude Code다. Claude Code에서는 메모리 표현을 직접 바꿀 수 있다(CLAUDE.md, auto memory, notes/ 같은 파일).
headless 모드(`-p --output-format stream-json`)는 시도마다 시간, 토큰, 도구 호출을 기계적으로 기록할 수 있다.
그래서 화면을 보고 손으로 세는 것보다 측정 오차가 작다.

**정리**: "같은 코딩 작업을 notes와 함께 다시 풀면 더 빠르다"는 주장을 직접 측정한 연구는 찾지 못했다.

- 학술 근거는 정확도 향상만 보였다(Reflexion, ExpeL, AWM). 그나마 작업마다 결과가 섞여 있다(Reflexion의 MBPP, Voyager의 돌 단계).
- 시간·속도 측정은 AWM의 단계 수가 유일하다.
- 벤더 자료는 기능이 어떻게 작동하는지만 설명하고 측정은 없다.

그래서 이 가설은 논문 수치를 그대로 믿지 않고, 내 환경에서 재현하거나 반박해야 할 대상이다.

## 3. 실험 설계

### 작업 (fixture/, 원본 고정)

교안 노트에 "버그가 쉬우면 두 조건 모두 성공해 차이가 안 보인다"는 지적이 있었다.
그래서 작업마다 테스트를 읽지 않으면 첫 시도에 걸리기 쉬운 함정을 하나 이상 넣었다.

| 작업 | 요청 | 확인 | 함정 |
|---|---|---|---|
| parse-log | `sample.log`에서 ERROR 줄만 표로 출력하는 `parse.py` 작성 | `test_parse.py` | INFO/DEBUG 메시지 안의 "ERROR" 문자열, 소문자 `error`, 여러 줄 Traceback, 메시지 안의 `|`는 `\|`로 이스케이프 |
| refactor-util | `util.py` 함수 3개에 타입 힌트·독스트링 추가 | `test_util.py` | 독스트링에 `Args:`/`Returns:` 절 필수, `safe_div` 반환과 `ignore` 인자는 `None` 포함 힌트 필수 |
| fix-failing | `test_me.py` 실패 2건 수정 | `test_me.py` | 할인 계산 버그, 그리고 `round()`의 은행가 반올림·부동소수 오차(`1.005`) → `Decimal` + `ROUND_HALF_UP` 필요 |

세 테스트 모두 원본 상태에서 실패한다. 기준 풀이로는 통과하는 것을 실행 전에 확인했다.

### 설계 표

| 구분 | 내용 |
|---|---|
| 고정 | Claude Code 2.1.299 headless, 모델 `claude-sonnet-5-5`, 같은 작업 3개와 fixture(시도마다 새로 복사), 같은 요청 문장, `acceptEdits` + `Bash(python:*)` 허용, MCP 없음, **auto memory 끔**(대조 조건에 경험이 새지 않게), 시도당 최대 3회 요청, 시도마다 새 세션 |
| 조작 (하나) | **메모리 표현: notes/의 내용** — A 경험 기록(1차 시도 직후 Claude가 쓴 3줄 노트) / B 대조(notes 없음) / C 위약(같은 형식의 일반론 3줄, 요청 문장은 A와 동일) |
| 이중 측정 | 해결률(3회 안에 테스트 통과 + 테스트 파일 무변경)과 함께 시간(벽시계, 재요청 포함), 시도 수, 입력·출력 토큰, 편집 횟수, 도구 호출 수, 권한 거부 수(=사람이 승인해야 했을 횟수), 비용 |
| 반론 | ① "빨라진 건 기록 내용이 아니라 'notes를 먼저 읽어라'는 지시가 신중하게 만든 것" → **위약 조건 C**로 구분 ② "실행마다 편차가 커서 한 번 비교로는 우연" → 2차 시도를 조건마다 **3회 반복**하고 중앙값과 범위 보고 ③ "B도 auto memory로 경험을 쌓았을 것" → auto memory를 끔 |
| 사전 판정식 | 작업별 3회 중앙값 기준. "A가 X보다 낫다" = 해결률 ≥ **그리고** 시간 10% 이상 짧음 **그리고** 시도 수 ≤. A>B가 2/3 이상 **그리고** A>C가 2/3 이상이면 **지지**. A>B만 2/3 이상이면 **부분 지지(원인 설명 기각)**. A>B가 1개 이하면 **기각**. 토큰·편집은 판정에 쓰지 않는다. |

### 측정값을 세는 방법

교안의 `/usage` 방식 대신 headless 실행의 stream-json 기록을 그대로 쓴다. 같은 세션 단위 집계를 기계적으로 남기기 위해서다.

| 측정값 | 세는 방법 |
|---|---|
| 소요 시간 | `claude -p` 프로세스 시작부터 끝까지의 벽시계 시간(초). 재요청한 경우 합산 |
| 토큰 | stream-json `result` 이벤트의 `usage`. 입력은 `input + cache_creation + cache_read`, 출력은 `output_tokens` |
| 편집 횟수 | Edit/Write/NotebookEdit 호출, 그리고 파일에 쓰는 Bash/PowerShell 명령(리다이렉트 `>`, `sed -i`, `tee`, `Set-Content` 등). 리허설에서 모델이 Edit 대신 `cat > shop.py <<EOF`로 고치는 것을 보고 실행 전에 추가했다 |
| 시도 수 | 테스트가 통과할 때까지 보낸 요청 수(최대 3). 실패하면 같은 세션에 "테스트가 아직 실패해…"를 보낸다 |
| 권한 거부 | `result.permission_denials` 개수. headless에서는 승인 창 대신 거부로 남는다 |

### 실행 절차

[`scripts/run_all.sh`](scripts/run_all.sh) → [`scripts/run_trial.py`](scripts/run_trial.py)

1. 저장소 밖 폴더(`C:\mh\runs`)에 시도마다 `fixture/`를 새로 복사한다.
2. 1차 시도: 작업마다 A, B를 한 번씩 푼다. A는 끝난 직후 같은 세션에서 `notes/<task>.md`에 3줄 노트를 쓰게 한다. 이 노트 작성은 지표에 넣지 않는다.
3. 2차 시도: 작업 파일을 원본으로 되돌린 새 폴더에서, 작업마다 A→B→C를 3회 번갈아 실행한다. A에는 1차에서 쓴 notes/, C에는 위약 notes/를 넣는다.
4. [`scripts/analyze.py`](scripts/analyze.py)로 집계하고 판정식을 적용한다.

## 4. 실행 기록

모두 실행했다. 1차 시도 6회, A의 notes 작성 3회, 2차 시도 27회로 총 36번의 headless 세션이다. 모든 시도는 실패 없이 끝났다.

| 경로 | 내용 |
|---|---|
| [`traces/`](traces/) | 시도마다 stream-json 원본 기록. 파일 이름은 `r<차수>_<조건>_<작업>_<반복>.jsonl` |
| 수정 전(before) | 조건 B, 기록 없음: `traces/r2_B_*.jsonl` |
| 수정 후(after) | 조건 A, notes/ 참조: `traces/r2_A_*.jsonl` |
| 위약 | 조건 C: `traces/r2_C_*.jsonl` |
| 1차 시도와 notes 작성 | `traces/r1_*.jsonl`, `traces/r1_A_*_notes.jsonl` |
| A가 쓴 notes | [`traces/notesA_snapshot/`](traces/notesA_snapshot/) |
| 위약 notes | [`scripts/placebo_notes/`](scripts/placebo_notes/) |
| 시도별 지표 | [`results.jsonl`](results.jsonl) (33행, notes 작성 3회는 지표에서 제외) |
| 집계표 | [`traces/summary.md`](traces/summary.md) (`python scripts/analyze.py`로 다시 만들 수 있음) |

### 실행 중에 확인한 사실

- **1차 시도는 6회 모두 첫 요청에 통과했다.** 일부러 넣은 함정(반올림, `Optional`, `|` 이스케이프)에 걸리지 않았다. 모델이 테스트 파일부터 읽고 요구사항을 맞췄기 때문이다.
- 그래서 A가 쓴 notes 3개 가운데 2개는 "만난 오류: 없음"이다. fix-failing 노트만 실패 메시지와 해결(`Decimal` + `ROUND_HALF_UP`)을 담았다.
  parse-log 노트는 테스트 실패가 아니라 도구 쪽 오류를 적었다. bash heredoc 명령이 거부되었으니 Write 도구를 쓰라는 내용이다.

| fix-failing | B 대조 | 3/3 | 74.4 (63~77) | 1 | 1 | 4 | 148,796 | 899 | **1** |
| fix-failing | C 위약 | 3/3 | 54.2 (53~55) | 1 | 1 | 8 | 149,384 | 1,155 | 0 |

권한 거부는 3회 합계다. 1차 시도 표는 [`traces/summary.md`](traces/summary.md)에 있다.

### 사전 판정식 적용

| 작업 | A vs B | A vs C |
|---|---|---|
| parse-log | **A가 나음** (54s vs 66s, −17%, 범위 안 겹침) | 아님 (54s vs 56s, −3%) |
| refactor-util | 아님 (54s vs 50s, A가 더 느림) | 아님 (54s vs 52s) |
| fix-failing | **A가 나음** (53s vs 74s, −29%, 범위는 63s에서 맞닿음) | 아님 (53s vs 54s, −2%) |

**판정: 부분 지지 (원인 설명 기각).**
A는 B보다 2/3 작업에서 빨랐다. 하지만 위약 C보다 나은 작업은 0/3이었다.
"notes가 있으면 두 번째 시도가 빨라진다"는 관찰은 재현됐다.
그러나 "그 효과가 기록의 내용에서 온다"는 원인 설명은 사전 판정식에 따라 기각한다.

시도 수는 모든 칸이 1이었다. 그래서 이 실험에서 시도 수는 조건을 구분하지 못했다.
"시간과 시도 수가 모두 적어야 한다"는 교안식 기준을 그대로 썼다면, 같은 시도 수가 '적음'이 아니므로 모든 작업에서 기각이었다.

## 6. 돌아보기: 불편의 원인이 정말 메모리 기능이었나

**아니었다. 적어도 이 환경에서 측정된 차이의 원인은 기록 내용이 아니라 행동 경로와 권한 정책의 상호작용이었다.**

trace에서 각 시도의 도구 호출 순서를 뽑아 보면 이유가 드러난다.

- **B(기록 없음)** 는 처음에 `Bash`로 테스트를 돌리거나 파일을 보고, 파일을 **bash heredoc(`cat > parse.py <<'EOF'`)으로 쓰려고** 했다.
  이 명령은 고정한 권한 설정(`acceptEdits` + `Bash(python:*)`만 허용)에서 거부되었다.
  모델은 거부를 받은 뒤에야 Write 도구로 다시 썼다. parse-log 3/3회, fix-failing 1/3회에서 이 거부-재시도가 있었다.
  B가 느렸던 두 작업이 정확히 거부가 있었던 작업이다.
- **A와 C** 는 "notes를 먼저 읽어라"라는 한 문장 때문에 `Glob → Read(notes) → Read(테스트·소스)`로 시작했다.
  읽기 모드로 들어간 뒤에는 **처음부터 Write 도구**로 파일을 썼고, 권한 거부는 0회였다.
  위약 노트에는 작업 정보가 전혀 없었지만 같은 경로를 탔고 시간도 같았다.
- **refactor-util** 에서는 B도 처음부터 `Read → Write`로 갔다. 거부가 없었고 가장 빨랐다.
  A는 notes 3개를 읽는 비용(입력 토큰 112k → 190k, 도구 호출 4 → 8)만 더 냈다.

그러니 1단계에서 느낀 불편 "새 세션이 지난 교훈을 잊어서 늦어진다"는 이 실험에서는 확인되지 않았다.

- 모델은 기록이 없어도 테스트를 읽고 함정을 피했다. 1차 6회 모두 한 번에 통과했다.
- 시간을 잡아먹은 것은 **"셸로 파일을 쓰다 권한에 막히는 행동"** 이었다.
- 이 행동은 노트의 내용이 아니라 "먼저 읽어라"라는 요청 문장으로 바뀌었다.

원인 후보로 의심했던 것 가운데 **요청 문장**과 **권한 정책**이 실제 원인에 가깝다.

### 원인 설명을 약하게 만든 것

- **실험한 작업이 실제 불편과 종류가 다르다.** 실제 불편은 사업 구상처럼 정답이 없는 대화에서 생겼다. 거기서는 지난 결정(방향, 조건)이 사라지면 모델이 스스로 되찾을 방법이 없다.
  반면 이번 코딩 작업은 테스트 파일에 요구사항이 다 적혀 있었다. 그래서 모델이 기록 없이도 테스트를 읽고 교훈을 그때그때 다시 얻었다.
  **"기록 없이 되찾을 수 없는 정보"가 있는 작업이어야 경험 기록의 내용 효과를 시험할 수 있다.** 이번 결과가 그 효과가 없다는 뜻은 아니다.
- **작업이 모델에게 너무 쉬웠다.** 함정을 넣었지만 1차 시도가 모두 한 번에 통과했다. 그래서 notes에 쓸 교훈이 거의 없었다(3개 중 2개가 "오류 없음"). 기록이 도울 여지 자체가 작았다.
- **n=3이다.** fix-failing의 A·B 범위는 63s에서 맞닿는다. 작은 표본이라 10% 기준을 넘었어도 차이는 약하다고 봐야 한다.
- **notes가 작업별로 나뉘지 않았다.** A는 다른 작업의 노트까지 읽느라 토큰을 더 썼다(fix-failing에서 3개 모두 읽음). 교안 예시대로 notes/ 폴더 전체를 넣었기 때문이다.
- **세 작업을 병렬로 돌렸다.** 같은 시각에 API 부하를 나눠 썼다. 조건은 번갈아 돌려서 부하가 한쪽 조건에만 쏠리지는 않게 했지만, 시간 측정의 잡음은 남는다.

### 확인한 범위와 미확인 사항

| 확인함 | 미확인 |
|---|---|
| Sonnet 5.5, Claude Code 2.1.299, Windows, 이 세 작업에서 notes+읽기 지시가 B보다 2/3 작업에서 10% 이상 빠름 | 다른 모델(Opus, Haiku)이나 다른 effort에서도 같은지 |
| 그 차이가 위약 노트로도 똑같이 생김(내용 효과 없음) | 모델이 1차에서 실제로 실패하는 어려운 작업에서 내용 효과가 생기는지 |
| B의 지연은 셸 heredoc 쓰기가 권한에 거부된 뒤 재시도한 것과 겹침 | 권한 규칙만 바꿨을 때(heredoc 허용 또는 Write 유도) B의 지연이 사라지는지. 이건 다음 실험에서 따로 조작해야 한다 |
| 해결률은 모든 조건 100%, 테스트 파일 변조 0건 | 대화형 세션(사람이 승인 창을 누르는 상황)에서 같은 차이가 나는지. headless에서는 승인 창 대신 거부가 된다 |

## 7. 다음 실험 계획과 재검토 조건

> 1번(권한 정책)은 실행했다. 결과는 [experiment-02.md](experiment-02.md)에 있다.
> 판정은 부분 지지다. auto 모드는 거부를 10건에서 0건으로 없앴지만, 빨라진 것은 parse-log(−16%)뿐이었다.
> 사후 분석에서는 셸 호출 1회에 약 7초가 든다는 것이 실제 시간 차이를 설명했다.

**다음 실험 (실험 02)**: 이번에 원인 후보로 드러난 두 가지를 각각 하나씩만 조작한다.

1. **권한 정책** (고정: 기록 없음). 조작은 heredoc 쓰기가 거부되는 지금 규칙 vs `Bash(cat:*)`를 허용하거나 셸 쓰기를 deny로 명시해 처음부터 Write를 쓰게 하는 규칙이다.
   측정은 권한 거부 수와 시간이다. 가설은 "거부가 0이 되면 B와 A의 시간 차이가 10% 안으로 줄어든다"이다.
2. **요청 문장** (고정: 지금 권한 규칙, notes 없음). 조작은 "먼저 관련 파일을 읽고 시작해" 한 문장의 유무다.
   위약 C에서 본 효과가 노트 파일 없이 문장만으로도 생기는지 확인한다.
3. 경험 기록 가설을 다시 시험하려면 **모델이 1차에서 실제로 실패하는 작업**이 먼저 필요하다.
   예를 들면 테스트에 드러나지 않는 숨은 요구, 여러 파일에 걸친 수정, 환경 특이점(Windows 경로·인코딩)이다.
   notes는 해당 작업 파일만 넣는다. 반복은 5회 이상으로 늘린다.
   실제 불편에 더 가깝게 하려면 **테스트나 파일에 없는 결정**(예: "출력은 CSV가 아니라 표로 하기로 했다")을 첫 세션 대화에서만 정하고, 두 번째 세션이 그 결정을 지키는지 측정한다.
4. **긴 대화 안에서의 혼동** (1단계 불편 2번). 컨텍스트 관리 절의 실습처럼 긴 원본 세션을 포크한다.
   조작은 그대로 둠, `/compact`, `context.md`로 요약한 뒤 새 세션에서 이어 가기 가운데 하나다.
   측정은 앞에서 정한 조건을 몇 개나 정확히 기억하는지(사전에 정한 질문 목록 정답률)와 토큰이다.

**이 결론을 다시 검토할 조건**

- 1차 시도에서 실패가 생기는 작업에서, A가 C보다 2/3 이상 작업에서 10% 이상 빠르면 → 원인 설명 기각을 철회하고 "내용 효과는 작업이 어려울 때만 나타난다"로 고친다.
- 권한 규칙을 바꿔 거부를 없앴는데도 B가 여전히 느리면 → "권한 거부가 원인"이라는 이번 해석을 버린다.
- Claude Code 버전이나 모델 기본 동작이 바뀌어 B가 처음부터 Write를 쓰면 → 이번 A·B 차이는 재현되지 않을 수 있으므로 다시 잰다.
