# 사전 등록: 실험 02 (결과를 보기 전에 작성, 2026-10-16)

실험 01의 돌아보기에서 나온 해석을 검증한다.
해석: "기록 없는 조건(B)이 느렸던 것은 셸 heredoc 쓰기가 Claude Code의 셸 보안 검사에 거부된 뒤 Write로 다시 쓰느라 그랬다."

## 실행 전 확인한 사실

- 실험 01 B의 거부 4건은 allow 규칙이 없어서가 아니라 **셸 보안 검사**에서 나왔다.
  - parse-log 3건: "Contains brace with quote character (expansion obfuscation)"
  - fix-failing 1건: "Parser skipped input between top-level statements"
  - 그래서 allow 규칙(`Bash(cat:*)` 등)을 넓히는 대신 **권한 모드**를 조작 항목으로 고른다.
- `bypassPermissions`는 교안 권고(격리 환경에서만)에 따라 쓰지 않는다.
- 리허설 1회(parse-log, auto 모드)는 거부 0회, 51.0초였다. 모델이 heredoc을 시도하지 않고 처음부터 Write를 썼다. 이 리허설은 데이터에 넣지 않는다.

## 가설 (반증 가능)

기록 없는 조건에서 권한 모드만 `acceptEdits` → `auto`로 바꾸면 다음이 함께 성립한다.

1. 실험 01에서 거부가 있었던 두 작업(parse-log, fix-failing)에서는 권한 거부가 줄고, 시간 중앙값이 10% 이상 짧아진다.
2. 거부가 없었던 refactor-util에서는 시간 차이가 10% 미만이다.

## 고정

실험 01과 같다. 모델 `claude-sonnet-5-5`, Claude Code 2.1.299 headless, 같은 fixture와 요청 문장(B와 동일, notes 없음),
`Bash(python:*)` 허용, MCP 없음, auto memory 끔, 시도마다 새 세션, 최대 3회 요청.

## 조작 (하나: 권한 모드)

| 조건 | 권한 모드 |
|---|---|
| P0 | `acceptEdits` (실험 01과 같음, 같은 시간대에 다시 측정) |
| P1 | `auto` (위험한 명령은 분류기가 판단) |

조건마다 5회씩, 작업별로 P0→P1을 번갈아 실행한다. 작업 3개는 병렬로 돌린다.

## 측정

- 주 지표: 소요 시간, 권한 거부 수, 해결률
- 보조 지표: 시도 수, 토큰, 편집 횟수, 도구 호출, 첫 쓰기 방식(셸 heredoc인지 Write 도구인지)

## 사전 판정식

작업별로 5회의 중앙값을 비교한다.

- **지지**: parse-log와 fix-failing **둘 다** "P1 해결률 ≥ P0, P1 거부 합계 < P0 거부 합계, P1 시간 ≤ P0의 0.9배"를 만족한다. **그리고** refactor-util의 시간 차이가 10% 미만이다.
- **부분 지지**: parse-log와 fix-failing 중 하나만 위 조건을 만족한다.
- **기각**: 둘 다 만족하지 않는다. 또는 거부가 줄었는데도 시간이 줄지 않는다. 이 경우 "권한 거부가 원인"이라는 실험 01의 해석을 버린다.
- **판정 불가**: P0에서 거부가 한 건도 재현되지 않는다. 비교의 전제가 성립하지 않으므로 판정하지 않고 그대로 보고한다.

해석상 주의: auto 모드는 거부 여부만이 아니라 모델의 첫 행동(heredoc 시도 여부)도 바꿀 수 있다. 이 효과는 둘로 나누지 않고 "권한 모드 효과"로 보고한다.
